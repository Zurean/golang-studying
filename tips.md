# Памятка по организации Go CLI-проекта

## Что требуется по инфраструктуре

- Разместить проект в GitHub-репозитории. По рекомендации ментора можно хранить все учебные задания в одном репозитории.
- Организовать код по пакетам: вычислительная логика отдельно, запуск и CLI отдельно.
- Добавить `.gitignore`, `Makefile`, `go.mod` и `.golangci-lint.yaml`.
- Реализовать консольный запуск всех требуемых сценариев.
- Проверять входные данные и возвращать понятные ошибки.
- Покрыть функциональность тестами с `testify`.
- Использовать табличные тесты там, где несколько случаев проверяются одинаковым способом.
- Настроить и запускать `golangci-lint`.

Неоднозначности в условии, которые стоит уточнить у ментора:

- В тексте одновременно требуются структура `Point` и интерфейс `Point`. Два типа с одинаковым именем нельзя объявить в одном Go-пакете.
- В интерфейсе `Figure` есть `Perimeter()`, но CLI-пример для периметра отсутствует. Метод и его тесты нужны, необходимость отдельной CLI-команды не уточнена.
- Не определено, должен ли репозиторий со всеми заданиями иметь один общий `go.mod` или отдельный модуль для каждого задания.

## 1. Структура проекта

У Go нет единственной обязательной структуры. Для небольшой CLI-утилиты возможна такая организация:

```text
project/
├── cmd/
│   └── app/
│       └── main.go
├── internal/
│   ├── cli/
│   │   ├── cli.go
│   │   └── cli_test.go
│   └── geometry/
│       ├── geometry.go
│       └── geometry_test.go
├── .gitignore
├── .golangci-lint.yaml
├── go.mod
├── go.sum
├── Makefile
└── README.md
```

Для совсем небольшого задания допустим более простой вариант:

```text
project/
├── main.go
├── geometry/
│   ├── geometry.go
│   └── geometry_test.go
├── .gitignore
├── .golangci-lint.yaml
├── go.mod
└── Makefile
```

Основные правила:

- Один каталог с `.go`-файлами — один пакет. В одном каталоге нельзя смешивать `package main` и `package geometry`.
- `package main` и `func main()` образуют исполняемую программу.
- `cmd/<имя>/main.go` — распространённое место для точки входа, но для одной маленькой команды `main.go` в корне тоже допустим.
- `internal/...` используют для пакетов, которые не должны импортироваться из других модулей.
- Обычный каталог `geometry/` делает пакет доступным для импорта другим модулям.
- Тесты обычно располагаются рядом с тестируемым кодом.

### Что означает «в main не должно быть бизнес-логики»

`main` может:

1. получить `os.Args`;
2. запустить CLI/application-код;
3. вывести ошибку;
4. завершить процесс с нужным exit code.

В `main` не следует помещать вычисления, правила предметной области и сложный разбор данных. Удобно иметь тестируемую функцию уровня приложения, которая получает аргументы и потоки ввода-вывода, а `main()` только вызывает её.

## 2. Makefile

Makefile хранит короткие одинаковые команды для локальной разработки и CI. Типичные цели:

```make
.PHONY: build run test test-cover lint fmt tidy clean

build:
	go build ./...

run:
	go run ./cmd/app $(ARGS)

test:
	go test ./...

test-cover:
	go test -cover ./...

lint:
	golangci-lint run

fmt:
	gofmt -w .

tidy:
	go mod tidy
```

Пример передачи CLI-аргументов:

```bash
make run ARGS="distance --point=1,2 --point=3,4"
```

Нюансы:

- Makefile запускает инструменты, но не содержит бизнес-логику.
- Строки команд под целями начинаются с символа табуляции.
- `.PHONY` предотвращает конфликт имён целей с файлами.
- `make` не входит в поставку Go и в Windows может потребовать отдельной установки, WSL или Git Bash.
- В `README.md` полезно указать требуемые версии Go, `make` и `golangci-lint`.

## 3. `go.mod` и `go.sum`

`go.mod` определяет Go-модуль и содержит:

- путь модуля;
- минимальную версию Go;
- прямые и косвенные зависимости;
- при необходимости директивы `replace` и `exclude`.

Для опубликованного проекта путь обычно совпадает с адресом репозитория:

```go
module github.com/username/repository
```

Этот путь становится префиксом внутренних импортов:

```go
import "github.com/username/repository/internal/cli"
```

Основные команды:

```bash
go mod init github.com/username/repository
go get github.com/example/dependency
go mod tidy
```

Нюансы:

- Директива `go` задаёт минимальную требуемую версию Go, а не просто документирует локальную версию.
- Версию следует согласовать со средой ментора или CI.
- `go mod tidy` добавляет используемые зависимости и удаляет неиспользуемые.
- `go.sum` хранит контрольные суммы зависимостей. Его нужно коммитить и не следует добавлять в `.gitignore`.
- Если каждое задание является отдельным модулем, команды `go test ./...` из корня родительского репозитория не обходят вложенные модули автоматически.

## 4. Линтер

Компилятор отвечает за возможность собрать программу. Линтер дополнительно находит:

- подозрительный и потенциально ошибочный код;
- пропущенную обработку ошибок;
- неиспользуемые или избыточные конструкции;
- проблемы стиля и читаемости;
- чрезмерно сложные функции;
- некоторые ошибки, которые компилятор не обнаруживает.

Минимальная интеграция `golangci-lint`:

- в корне есть `.golangci-lint.yaml`;
- конфигурация соответствует установленной версии линтера;
- выполняется `golangci-lint run`;
- в Makefile есть цель `lint`;
- проверка завершается без ошибок.

Для актуального формата конфигурации v2 файл начинается так:

```yaml
version: "2"

linters:
  default: standard
```

Полезные команды:

```bash
golangci-lint run
golangci-lint config verify
golangci-lint --version
```

Нюансы:

- Не копировать старую конфигурацию без проверки: форматы разных основных версий несовместимы.
- Версию линтера желательно зафиксировать в `README.md` или CI.
- GitHub Actions полезен, но прямо из условия не следует. Конфигурация и локальная команда `make lint` — необходимый минимум.
- Линтер является инструментом разработки и обычно не добавляется как зависимость приложения в `go.mod`.

Документация: <https://golangci-lint.run/docs/configuration/file/>

## 5. Команды, аргументы и флаги CLI

Термины:

- **Команда/подкоманда** выбирает действие: `app distance`.
- **Флаг** — именованный параметр: `--radius=10`.
- **Позиционный аргумент** — значение без имени: `app distance 1,2 3,4`.
- **Опция** — общее разговорное название настройки команды.

Возможны два стиля интерфейса.

Выбор действия булевым флагом:

```bash
app --distance --point=1,2 --point=3,4
```

Выбор действия подкомандой:

```bash
app distance --point=1,2 --point=3,4
```

Подкоманды удобнее расширять и делают взаимоисключающие действия явными. В условии сказано, что названия и формат флагов могут отличаться, поэтому примеры не обязательно повторять буквально.

Типичные виды флагов:

```text
--polygon                 булевый
--radius=10               числовой
--point=1,2               строковый составной
--point=1,2 --point=3,4   повторяемый
```

Флаги считаются опциональными только на уровне синтаксиса библиотеки. Для выбранной команды некоторые из них могут быть обязательными по правилам приложения.

### Что проверять при разборе CLI

- известна ли команда или флаг;
- переданы ли обязательные данные;
- нет ли несовместимых режимов;
- правильное ли количество повторяемых значений;
- преобразуются ли строки в нужные типы;
- допустимы ли полученные значения;
- не остались ли неожиданные позиционные аргументы.

Парсинг и валидация — разные этапы:

1. Парсинг преобразует текстовые аргументы в типизированные значения.
2. Валидация проверяет полноту, совместимость и допустимость значений.
3. Только после этого вызывается предметная логика.

### Повторяемые флаги

Стандартный `flag` требует пользовательский тип, реализующий `flag.Value`, если один флаг должен накапливать несколько значений.

В `pflag` есть готовые варианты. Для значения, внутри которого уже используется запятая, предпочтителен `StringArray`: он накапливает каждое повторение флага как отдельную строку. `StringSlice` дополнительно разбивает строку по запятым и поэтому может быть неудобен для координат.

## 6. Ошибки, вывод и exit codes

Корректное поведение CLI:

- результат успешной команды записывается в `stdout`;
- диагностическое сообщение записывается в `stderr`;
- успешное выполнение возвращает exit code `0`;
- неверный запуск или ошибка выполнения возвращает ненулевой код;
- `--help` показывает синтаксис и список доступных команд/флагов;
- сообщение об ошибке объясняет проблему и по возможности показывает правильный формат.

Для удобства тестирования CLI-код не должен напрямую зависеть от глобальных `os.Args`, `os.Stdout` и `os.Stderr`. Лучше передавать аргументы и `io.Writer` в отдельную функцию, а обращаться к `os` только в `main()`.

Не нужно вызывать `os.Exit` глубоко внутри пакетов: он немедленно завершает процесс и мешает тестированию. Решение об exit code удобно оставлять точке входа.

## 7. Библиотеки для CLI и роутинга

### `flag`

Стандартный пакет Go.

Плюсы:

- нет внешней зависимости;
- достаточно для небольшого плоского CLI;
- поддерживает отдельные `flag.FlagSet` для самостоятельной организации подкоманд.

Минусы:

- роутинг подкоманд реализуется вручную;
- повторяемые составные флаги требуют собственного `flag.Value`;
- меньше готовых возможностей для help/usage.

Документация: <https://pkg.go.dev/flag>

### `pflag`

Совместим по идее со стандартным `flag`, но предоставляет привычные POSIX/GNU-флаги, короткие имена и готовые массивы.

Подходит, если нужен сравнительно простой CLI без полноценного фреймворка. Для этого задания это разумный базовый выбор, так как он прямо указан ментором.

Документация: <https://pkg.go.dev/github.com/spf13/pflag>

### Cobra

Полноценный CLI-роутер поверх `pflag`. Предоставляет:

- подкоманды и вложенные команды;
- автоматические `help` и `usage`;
- локальные и глобальные флаги;
- проверку неизвестных команд;
- генерацию shell completion.

Подходит для структуры `app command --flag`. Для трёх простых действий может оказаться избыточным, но полезен, если цель — изучить полноценную организацию CLI.

Документация: <https://github.com/spf13/cobra>

### Практический выбор

- Нужен минимальный учебный вариант без зависимостей — `flag`.
- Нужны повторяемые флаги и привычный синтаксис — `pflag`.
- Нужны настоящие подкоманды, автоматический help и готовый роутинг — Cobra.
- Не стоит одновременно самостоятельно строить сложный роутер и подключать Cobra: выбрать один подход и последовательно его использовать.

## 8. Тесты в Go

Основные правила:

- имя файла заканчивается на `_test.go`;
- имя тестовой функции начинается с `Test`;
- функция принимает `t *testing.T`;
- тесты располагаются в том же каталоге, что и тестируемый пакет;
- каждый тест должен быть независим от порядка выполнения других тестов.

Минимальный каркас:

```go
func TestSomething(t *testing.T) {
    // arrange: подготовить входные данные
    // act: вызвать тестируемый код
    // assert: проверить результат и ошибку
}
```

Команды запуска:

```bash
go test ./...          # все пакеты текущего модуля
go test -v ./...       # подробный вывод
go test -cover ./...   # оценка покрытия
go test -race ./...    # поиск гонок данных
go test ./path/pkg     # конкретный пакет
go test -run TestName ./... # выбранный тест
```

### `testify`

По условию нужно использовать пакет `testify`:

```bash
go get github.com/stretchr/testify
go mod tidy
```

- `assert` сообщает о неудачной проверке и продолжает текущий тест.
- `require` сообщает о неудаче и немедленно прекращает текущий тест или подтест.
- Сначала удобно проверять ошибку через `require`, затем остальные результаты через `assert`.
- Для `float64` обычно используют сравнение с допустимой погрешностью, например `assert.InDelta`, а не строгое `assert.Equal`.

Покрывать следует не только успешные случаи, но также границы и ошибки. В рамках этого проекта требование «весь функционал» разумно понимать как проверки предметных методов, парсинга, валидации и поведения CLI.

Документация по тестам: <https://go.dev/doc/tutorial/add-a-test>

## 9. Табличные тесты

Табличный тест хранит сценарии в срезе структур, а общую процедуру проверки выполняет в цикле:

```go
func TestParse(t *testing.T) {
    tests := []struct {
        name    string
        input   string
        want    string
        wantErr bool
    }{
        // тестовые случаи
    }

    for _, tt := range tests {
        t.Run(tt.name, func(t *testing.T) {
            got, err := parse(tt.input)

            if tt.wantErr {
                require.Error(t, err)
                return
            }

            require.NoError(t, err)
            assert.Equal(t, tt.want, got)
        })
    }
}
```

Подходит, когда:

- одна функция проверяется на разных входах;
- у случаев одинаковая подготовка и одинаковый способ проверки;
- проверяются валидные, граничные и ошибочные значения;
- без таблицы появляется копирование почти одинакового тестового кода.

Не нужно применять насильно, когда:

- сценарии имеют принципиально разную подготовку;
- требуются совершенно разные проверки;
- тест представляет длинный последовательный процесс;
- таблица стала сложнее и менее понятна, чем отдельные тесты.

Каждому случаю следует давать понятное `name` и запускать его через `t.Run`, чтобы при ошибке было видно, какой сценарий сломался.

Документация: <https://go.dev/wiki/TableDrivenTests>

## 10. Git и репозиторий

Минимально ожидается:

- инициализированный Git-репозиторий;
- осмысленные коммиты;
- remote на GitHub;
- исходники и инфраструктурные файлы отправлены в репозиторий;
- результаты сборки и локальные файлы IDE исключены через `.gitignore`.

Обычно коммитят:

```text
*.go
*_test.go
go.mod
go.sum
Makefile
.golangci-lint.yaml
.gitignore
README.md
```

Обычно не коммитят:

```text
собранные бинарники
coverage.out и другие временные отчёты
локальные каталоги IDE
временные файлы ОС
```
